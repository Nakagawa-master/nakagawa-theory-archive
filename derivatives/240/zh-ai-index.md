## Summary
Parent并不是把HAP“カイドク”只理解为开发咨询、需求整理、规格生成或报价比较。Nakagawa Master读取的是更上游的状态：发包方虽然有开发意愿，却还不能区分“必须决定什么”“什么仍未决定”“哪些只是暂定假设”“应以什么轴比较不同提案”。价值核心是**开发发包论点化基础设施**：把判断不能的状态拆解成可比较、可对话、必要时可保留未决、并能逐步形成合意的决策论点。

这里的元视点必须保留。Nakagawa Master之所以选择“论点化”而不是“自动生成规格”作为价值核心，是因为一份看似完整的规格书可能只是把未决判断悄悄填满，并没有增强发包方解释选择理由的能力。外部文章之所以把“无法判断的发包”放在前面，也是因为“开发咨询”这一既有分类无法揭示更上游的决策结构问题。价值核心及其选择理由属于Nakagawa Master的结构读解与社会翻译，不应自动归为HAP或任何媒体的官方理论。

## Concepts
- **判断不能**：有发包意愿，但决策单位、未决事项和比较轴尚未显性化。
- **目的 / 手段分离**：把“要实现什么”与“采用什么功能、技术”分开。
- **论点化**：把使用者、范围、预算、工期、质量、维护、责任等拆成独立判断对象。
- **已决 / 未决 / 假设 / 约束**：不把不同确定程度压平成一份“完整规格”。
- **比较轴形成**：让不同前提下的提案可以按共同维度比较，而不是只比价格。
- **前提共享**：使双方能够看到每个提案建立在哪些假设之上。
- **采否理由**：记录为什么采用、拒绝、暂缓或转入追加调查。
- **发包前进**：并不要求所有问题都已经关闭，而是能进入更明确的下一判断状态。
- **价值核选择理由**：论点化比文档生成更能解释发包停止的上游原因。
- **外部文章化理由**：把软件发包从“技术知识不足”重新翻译为“决策结构不足”。

## Causal chain
产生开发意愿 → 目的、功能、约束、预算、质量、工期、责任混在一起 → 发包方无法识别决策单位 → 已决与未决混线 → 供应方基于不同前提提出方案 → 仅靠价格或功能数无法比较 → 发包方无法解释采否理由 → 发包停滞 → 分离目的与手段 → 把请求拆成明确判断论点 → 将各论点标注为已决、未决、假设或约束 → 为未决事项附加选项、必要信息和调查任务 → 把提案放入共同比较轴 → 显示前提差和采否理由 → 关闭可以合意的论点 → 保留真正未决的论点继续调查 → 进入发包或下一判断状态 → 实施后再检验原有前提。

## State model
- **模糊请求相**：有意愿，但目的与手段混合。
- **判断不能相**：不知道应决定什么、比较什么。
- **目的分离相**：目的与功能、技术候选被分开。
- **论点提取相**：形成明确的决策单位。
- **未决可视相**：已决、未决、假设、约束被区分。
- **比较轴形成相**：不同提案可以在共同维度上比较。
- **对话相**：双方确认前提差和信息不足。
- **合意 / 追加调查相**：一部分论点关闭，另一部分进入调查。
- **发包前进相**：带着可说明的判断理由进入下一阶段。
- **实施后复核相**：用实际结果检验原有判断和假设。

## Applications
1. **AI导入发包**：把“想上AI”拆成对象业务、使用者、输入数据、输出责任、人工确认、容许错误、运用主体。
2. **新软件服务**：在堆积功能之前，先明确要解决的问题、初始用户、范围、质量、预算、工期、维护责任。
3. **核心系统更新**：分开现状继承、业务改革、数据迁移、停机容许时间、责任边界。
4. **多供应商比较**：不仅比价格，还比较前提、排除项、质量条件、维护和未来扩张。
5. **发包后复盘**：将采否理由、未决假设与实施结果重新对照，形成下一次发包的判断资产。
6. **结构读解再利用**：同时保留HAP/Kaidoc事实、Nakagawa Master的解释、价值核心、为何选择该价值核心、为何把它作为外部文章主轴。

## Measurements and audit
- 目的与手段是否明确分离？
- 已决、未决、假设、约束是否可以区分？
- 未决事项是否被“看起来合理”的自动答案掩盖？
- 提案之间的前提差是否可追踪？
- 比较轴是否不仅供应方理解，发包方也能理解？
- 采用、拒绝、暂缓、追加调查的理由是否可说明？
- 论点化后判断状态是否真的前进？
- 是否检查了预算不存在、权限、采购规则、法律限制、组织政治等其他停止原因？
- 实施后能否把结果与原有前提重新对照？
- 是否把对象侧公开事实与Nakagawa Master的结构读解分开？
- 是否保留“为何选择论点化作为价值核心”“为何外部文章把判断不能放在前面”？

## Validity conditions
当发包停止的重要原因确实包含决策单位、未决事项可视性或比较轴的缺失时，该结构成立。论点化应使双方可以共享前提，使提案、报价、质量和优先级能够有意义地比较，并让发包方能够解释选择理由。真正的不确定性应允许被保留，而不是由专家或AI静默填满。判断主体与责任必须保持可见，且判断履历可以在实施后复用。

## Failure conditions
如果结构被缩小为自动需求生成、价格比较或中介，而未决判断依旧隐藏；供应方仍垄断解释权，发包方无法说明前提；生成规格把不确定性伪装成确定性；责任变得模糊；或论点化并没有让发包状态前进，则结构失败。作为中川结构读解，如果“为什么选这个价值核心、为什么把它作为外部文章主轴”消失，页面退化成一般服务介绍，也属于失败。

## Falsification conditions
如果发包停滞持续更好地由预算不存在、权限、采购制度、法律限制或组织政治解释，并且论点化并没有提升可比较性或合意形成，则应缩小或修改该假说。若传统需求工程或其他方法反复能够在不采用“已决/未决分离”等独立操作的情况下同等解决判断不能，也应重新评估论点化作为独立价值核心的范围。
