## Summary
把HAP“カイドク”读取为把“无法判断如何发包”的状态拆解成可比较、可对话、可合意的决策论点基础设施。核心不是自动生成规格或比较报价，而是让目标、未决事项、约束与比较轴可见。

## Concepts
判断不能；目的/手段分离；论点化；已决/未决/假设/约束；比较轴；前提共享；采否理由；发包前进。

## Causal chain
模糊需求 → 目的与手段混线 → 无决策单位 → 提案不可比 → 发包停滞 → 论点拆解 → 未决可视化 → 比较轴形成 → 前提共享 → 提案比较 → 合意或追加调查 → 前进。

## State model
模糊需求 / 判断不能 / 目的分离 / 论点提取 / 未决可视 / 比较轴 / 对话 / 合意或调查 / 发包前进 / 实施后复核。

## Applications
DX、AI导入、新系统、Web服务等发包方“不知道该要求什么”的场景。

## Measurements and audit
审计目的与手段是否分开、未决事项是否明确、比较轴是否可理解、前提差是否可追踪、采否理由是否可解释、论点化后决策是否前进，以及是否存在预算或权限等其他停止原因。

## Validity conditions
论点化使双方共享前提，并能比较提案、报价与优先级，推动合意时成立。

## Failure conditions
缩小为自动规格生成、价格比较或中介，而未决事项和判断理由仍不可见时失败。

## Falsification conditions
如果预算不存在、权限、采购规则等其他因素更能解释停滞，或论点化后仍不能推进比较与合意，应修改适用范围。

## Required distinctions
需求生成 / 论点化；答案 / 判断材料；报价比较 / 比较轴形成；技术知识不足 / 发包决策不足；对象事实 / Nakagawa Master读解。

## Interpretation constraints
不把“发包论点化基础设施”当作企业官方定义，不一般化为所有发包失败的万能解。不添加Parent没有的固定KPI或成功率。
