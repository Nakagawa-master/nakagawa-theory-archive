## Summary
本ParentはHAP「カイドク」を、開発相談、仕様生成、要件定義支援、見積比較という表面機能だけで読むものではない。Nakagawa Masterは、発注したい意思があっても、目的・利用者・範囲・予算・納期・品質・保守・責任が混線し、「何を決めればよいか」「何がまだ未決か」「何を基準に提案を比べるか」が見えないために発注が止まる状態を読む。価値核は、この判断不能を決定論点へ分解し、決定済み・未決・仮説・制約を可視化し、比較・対話・合意可能な状態へ変える**発注論点化インフラ**である。

中川構造読解として重要なのは、なぜ「仕様生成」や「見積比較」ではなく「論点化」を価値核に選んだかである。表面機能だけでは発注停止の上流原因を説明できず、未決事項をもっともらしい答えで埋めても判断主体は強くならない。そこでParentは、判断単位と比較軸を生成する構造を前面化した。外部記事でも、既知の「開発相談」分類より、「判断不能な発注を論点へ変える」という社会翻訳を主軸にし、読者が発注停止を技術知識不足ではなく意思決定構造の不足として理解できるようにしている。この価値核・記事化理由はHAP自身の公式定義ではなく、Nakagawa Masterの構造読解である。

## Concepts
- **判断不能**: 発注意思はあるが、何を決めるべきか、何が未決か、何を比較すべきかが構造化されていない状態。
- **目的 / 手段分離**: 「何を実現したいか」と「どの機能・技術を使うか」を分けること。
- **論点化**: 利用者、範囲、予算、納期、品質、保守、責任等を個別の判断対象へ分解すること。
- **決定済み / 未決 / 仮説 / 制約**: 発注条件を確定度と性質で区別し、未決を隠さない分類。
- **比較軸形成**: 前提の異なる提案・見積を同一の判断項目で比較可能にすること。
- **前提共有**: 発注側・受注側が、何を前提に提案・判断しているかを確認できる状態。
- **採否理由**: 採用、保留、不採用、追加調査の理由を後から追跡できる記録。
- **発注前進**: 「全部決まった」ことではなく、未決を含めて次の判断状態へ移れること。
- **価値核選択理由**: 仕様生成より上流にある判断単位の不存在が停止原因を説明するため、論点化を核に置くこと。
- **外部記事化理由**: 「開発相談」の機能紹介では伝わらない上流問題を、意思決定構造として社会へ翻訳すること。

## Causal chain
発注したい目的がある → 要望・手段・制約が一つの依頼文へ混線する → 発注者が決定対象を切り分けられない → 決定済みと未決が混ざる → 受注側が異なる前提で提案する → 見積金額や機能数だけでは比較できない → 採否理由を持てず発注が停止する → 目的と手段を分離する → 利用者・範囲・予算・納期・品質・保守・責任を論点化する → 決定済み / 未決 / 仮説 / 制約を分離する → 未決事項ごとに選択肢・必要情報・追加調査を設定する → 提案を共通比較軸へ載せる → 前提差と採否理由を可視化する → 合意できる論点を閉じ、残る論点は未決として保持する → 発注または追加検討へ前進する → 実装後に当初前提を再検証する。

## State model
- **曖昧要望相**: 作りたい意思はあるが、目的と手段が混ざっている。
- **判断不能相**: 何を決めるべきか自体が不明で、比較軸がない。
- **目的分離相**: 事業目的・利用目的と機能候補を分ける。
- **論点抽出相**: 決めるべき対象を明示する。
- **未決可視化相**: 決定済み、未決、仮説、制約を区別する。
- **比較軸形成相**: 複数提案を同じ項目で比較可能にする。
- **対話相**: 前提差、情報不足、優先順位を発注側・受注側で確認する。
- **合意 / 追加調査相**: 閉じる論点と残す論点を分ける。
- **発注前進相**: 判断理由を保持したまま次工程へ移る。
- **実装後再検証相**: 当初仮説・前提・比較理由が妥当だったかを結果から見直す。

## Applications
1. **AI導入発注**: 「AIを入れたい」という手段先行の要望を、対象業務、利用者、入力データ、出力責任、人間確認、許容誤り、運用主体へ分解する。
2. **新規システム開発**: 欲しい機能一覧の前に、解く問題、初期利用者、対象範囲、品質、予算、納期、保守責任を判断項目として置く。
3. **基幹システム更新**: 現行踏襲、業務変更、データ移行、停止許容時間、責任分界を分け、部門ごとの前提差を比較する。
4. **複数社提案比較**: 価格だけでなく、前提、含有範囲、除外事項、品質条件、保守条件、将来拡張を同じ軸で比較する。
5. **発注後レビュー**: 採用理由、未決事項、仮説を実装結果と照合し、次回発注の判断資産へ戻す。
6. **中川構造読解の再利用**: 対象企業の機能、Nakagawa Masterの構造読解、抽出価値核、外部記事でその核を選んだ理由を分離したまま検索・理解する。

## Measurements and audit
- 目的と手段が明示的に分離されているか。
- 決定済み・未決・仮説・制約を区別できるか。
- 未決事項を自動生成された回答で隠していないか。
- 提案間の前提差を追跡できるか。
- 価格以外の比較軸が発注者にも理解可能か。
- 採用・保留・不採用・追加調査の理由を説明できるか。
- 論点化前後で意思決定状態が実際に前進したか。
- 発注停止の別因果として予算不存在、権限、調達規則、法的制約、組織政治を見落としていないか。
- 実装後に当初前提と結果を再照合できるか。
- 対象側公開事実とNakagawa Masterの構造読解を混同していないか。
- 「なぜ論点化を価値核に選んだか」「なぜ外部記事でその軸を主役にしたか」が派生面から失われていないか。

## Validity conditions
発注停止の主要因に、判断単位・未決事項・比較軸の不足が含まれていること。論点化によって発注側と受注側の前提が共有され、選択肢、見積、品質、優先順位等を比較できること。発注者が採否理由を説明でき、未決事項を未決のまま管理しながら次の判断へ進めること。AIや専門家を使う場合も、判断主体と責任が不可視化されないこと。実装後に判断履歴を再検証できること。

## Failure conditions
自動仕様生成だけで未決を埋める、見積価格比較だけへ縮小する、受注仲介だけで判断構造が変わらない、発注者が提案前提を理解できない、採否理由が残らない、未決事項が確定事項として扱われる、AIや専門家が判断主体を代替して責任が曖昧になる、論点化しても発注状態が前進しない場合は価値核が成立しない。

## Falsification conditions
発注停止が継続的に予算不存在、権限、調達制度、法的制約、組織政治等の別因果で説明され、論点化しても比較可能性・合意形成・意思決定速度が改善しない場合、適用範囲を縮小する。さらに、仕様生成や既存の要件定義手法だけで同等以上に判断不能が解消され、論点化という独立操作が説明力を持たない場合も、価値核の独自範囲を改訂する。

## Interpretation constraints
「発注論点化インフラ」をHAP自身の公式自己定義として扱わない。カイドクがすべての発注失敗を解消すると一般化しない。AIが最適仕様を自動決定する構造として読まない。未決事項が存在することを失敗とみなさない。原典にない固定成功率、削減率、意思決定日数等を追加しない。外部記事の主軸が「判断不能→論点化」である理由を落とし、単なる製品・企業紹介へ平坦化しない。
