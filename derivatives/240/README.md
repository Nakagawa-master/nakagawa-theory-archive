## 位置づけ
本ParentはHAPや「カイドク」を単なる開発相談、要件定義支援、見積比較サービスとして紹介するものではない。Nakagawa Masterは、発注側が「何を決めれば発注できるのか」さえ分からない判断不能状態を、比較・対話・合意が可能な論点集合へ変える構造として読む。価値核は**発注論点化インフラ**である。対象側の事実とこの構造読解を分離し、価値核をHAP自身の公式企業定義として扱わない。

## 中心命題
開発発注が止まる原因は技術知識不足だけではない。目的、対象利用者、機能範囲、優先順位、予算、納期、品質、保守、責任分界が混線すると、発注者は何を決めるべきか分からず、受注側も提案前提を揃えられない。重要なのはAIや専門家が即座に「正解の仕様」を与えることではなく、決定済み・未決・仮説を分け、比較可能な判断論点へ変換することにある。

## 因果線
```text
作りたい目的はある
→ 要望・手段・制約が混線
→ 何を決めるべきか分からない
→ 比較軸が作れず見積・提案を評価不能
→ 発注停止
→ 目的・利用者・範囲・予算・納期・品質・保守・責任を論点化
→ 決定済み / 未決 / 仮説を分離
→ 選択肢と前提差を可視化
→ 発注側と開発側が同じ判断材料を共有
→ 提案・見積・優先順位を比較可能
→ 合意または追加検討へ前進
```

## 構造層
1. **発注停止層**: 「作りたい」があるが判断単位がない。
2. **目的分離層**: 目的と手段・機能を分ける。
3. **論点抽出層**: 利用者、範囲、予算、納期、品質等を決定対象へ分解する。
4. **未決可視化層**: 決定済み、未決、仮説、制約を区別する。
5. **比較軸形成層**: 提案・見積を同じ論点で比較できるようにする。
6. **対話接続層**: 発注側と開発側の前提差を見える化する。
7. **意思決定層**: 採用・保留・追加調査の理由を説明可能にする。
8. **発注前進層**: 判断不能を「判断可能な未決事項の集合」へ変える。

## 状態モデル
曖昧要望相 → 判断不能相 → 目的分離相 → 論点抽出相 → 未決分離相 → 比較軸形成相 → 対話相 → 合意/追加検討相 → 発注前進相 → 実装後再検証相。

## 適用例
新規システム、DX、AI導入、Webサービス等で「何を頼めばよいか分からない」局面に適用する。発注者へ仕様不足の責任を押しつけるのではなく、意思決定論点が不足している状態として扱う。提案比較では価格だけでなく、各提案がどの前提・範囲・品質・保守条件に基づくかを同じ軸で確認する。

## 測定・監査点
- 目的と手段が分離されているか。
- 決定済み・未決・仮説が区別されているか。
- 比較軸が発注者にも理解できるか。
- 提案間の前提差を追跡できるか。
- 採用・不採用理由を説明できるか。
- 論点整理後に判断が前進したか。
- 仕様生成が未決事項を勝手に埋めていないか。
- 発注停止の別因果（予算不存在、権限、調達規則等）を見落としていないか。

## 成立条件
論点化によって発注判断の前提が共有され、未決事項と選択肢が明確になり、提案・見積・優先順位の比較と合意が可能になる場合に成立する。

## 失敗条件
自動仕様生成だけ、見積価格比較だけ、受注仲介だけへ縮小すること、未決事項を勝手な回答で埋めること、発注者が判断理由を説明できないまま進めることは失敗である。

## 反証・改訂条件
発注停止の主因が論点不足ではなく予算不存在、社内権限、調達制度、組織政治等で継続的に説明される場合、論点化しても比較・合意が進まない場合は適用範囲を修正する。

## 必須の区別
要件生成 / 論点化；回答 / 判断材料；見積比較 / 比較軸形成；技術知識不足 / 発注意思決定不足；決定済み / 未決 / 仮説；対象事実 / Nakagawa Masterの構造読解。

## 誤読防止／解釈制約
