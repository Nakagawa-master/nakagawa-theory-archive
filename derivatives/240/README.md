## 位置づけ
このParentは開発会社や見積サービスの紹介ではなく、中川構造読解として、ソフトウェア開発の発注側が「何を決めれば発注できるか」さえ分からない判断不能状態を、論点へ分解し比較可能にする構造を読む。

## 中心命題
開発発注が止まる原因は、技術知識不足だけではない。目的、範囲、優先順位、予算、納期、品質、保守、責任分界が混線すると、発注者は比較条件を作れず、受注側も提案前提を固定できない。カイドクの価値核は、曖昧な要望を「答え」へ即変換することではなく、発注判断に必要な論点を可視化し、対話・比較・合意の入口を作る**発注論点化インフラ**として読める点にある。

## 因果線
`作りたいが要件を言語化できない → 評価軸がない → 見積・会社比較不能 → 発注停止 → 要望を論点へ分解 → 未決事項と選択肢を可視化 → 発注者と開発側の前提共有 → 比較・合意可能 → 開発発注が前進`

## 構造層
1. 発注停止層: 目的と手段が混線し、何を決めるべきか不明。
2. 論点抽出層: 目的、対象利用者、範囲、予算、納期、品質等へ分解。
3. 未決可視化層: 決定済み・未決・仮説を分ける。
4. 比較軸形成層: 提案や見積を同じ論点で比較できる状態を作る。
5. 対話接続層: 発注者と開発側が同じ判断材料を共有する。
6. 発注前進層: 判断不能を、判断可能な未決事項の集合へ変える。

## 状態モデル
曖昧要望 / 判断不能 / 論点抽出 / 未決分離 / 比較軸形成 / 対話 / 合意 / 発注前進 / 実装後再検証。

## 適用例
DX、新規システム、AI導入、Webサービス等で、発注者が「何を頼めばよいか分からない」局面を、仕様書不足として責めるのではなく、意思決定論点の不足として監査する。

## 測定・監査点
目的と手段が分離されているか／未決事項が明示されるか／比較軸が作られるか／発注者が理由を説明できるか／提案間の前提差を追跡できるか／論点整理後に判断が前進したかを確認する。

## 成立条件
論点化によって発注判断の前提が共有され、提案・見積・優先順位の比較が可能になる場合に成立する。

## 失敗条件
AIが自動で仕様を作るサービス、単なる見積比較、受注仲介へ縮小し、判断不能→論点化→比較可能化の因果を消すと失敗する。

## 反証・改訂条件
発注停止が論点不足ではなく、予算不存在、社内権限、調達規則等の別因果で継続的に説明される場合は適用範囲を修正する。

## 必須の区別
要件生成 / 論点化；回答 / 判断材料；見積比較 / 比較軸形成；技術知識不足 / 発注意思決定不足；企業公式見解 / Nakagawa Masterの構造読解。

## 誤読禁止 / 解釈制約
「カイドク」が全ての発注失敗を解消すると一般化しない。価値核「発注論点化インフラ」はNakagawa Masterの読解であり、企業公式の自己定義と混同しない。
