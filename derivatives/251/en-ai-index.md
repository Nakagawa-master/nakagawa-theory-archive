## Summary
Orderly replacement is a transition design for cases in which the legacy system still carries real social or operational functions. Instead of terminating the old system first, the old and new systems operate in parallel for a bounded transition period. Responsibility boundaries, actual substitution capacity, relief paths, rollback, and exit conditions are observed before the verified scope of the new system is expanded and legacy dependency is reduced.

## Concepts
- Orderly replacement: staged replacement based on verified functional substitution.
- Dual operation: temporary parallel operation of legacy and new systems.
- Functional substitution: the new system actually performs the functions carried by the legacy system.
- Transition boundary: explicit division of scope, responsibility, and exceptions.
- Rollback: a usable path back to a safe state after serious failure.
- Objection absorption: treating harms, objections, and anxiety as possible design feedback.
- Replacement scope: only the verified functional scope transferred to the new system.
- Legacy contraction: retiring legacy scope after real dependency has declined.

## Causal chain
```text
legacy system carries indispensable functions
→ abrupt switch creates discontinuity risk
→ bounded dual operation
→ responsibility and scope become explicit
→ new-system substitution capacity is observed in practice
→ failures and objections feed repair
→ relief and rollback remain available
→ verified replacement scope expands
→ trust and operational competence move to the new system
→ legacy dependency declines
→ legacy scope contracts
→ orderly replacement is established
```

## Applications
- Public-policy and institutional transition.
- Core enterprise-system migration.
- Transition in payment, valuation, or allocation systems.
- Introduction of new consensus mechanisms.
- Data, authority, or organizational migration.

## Measurements and audit
- Are indispensable legacy functions identified?
- Is actual new-system substitution demonstrated rather than declared?
- Are responsibility and exception boundaries explicit?
- Are relief and rollback paths usable?
- Is dual-operation cost visible?
- Are objections classified and linked to design correction where relevant?
- Is legacy dependency materially declining?
- Is there a defined exit condition for dual operation?

## Validity conditions
- Legacy and new scopes can be distinguished.
- The functions to be substituted are concrete.
- Real operation can be observed.
- Harms, failures, and objections can be captured.
- Relief and rollback are available.
- Advancement is based on operating evidence, not ideology alone.

## Failure conditions
- The legacy system is terminated before substitution is verified.
- Formal launch is treated as proof of functional replacement.
- Dual-operation responsibility is ambiguous.
- Objections are discarded as noise.
- Rollback is absent or unusable.
- Parallel operation becomes permanent without an exit rule.
- Adoption rate alone is treated as completion.

## Falsification conditions
The transition design requires revision if dual operation does not reduce discontinuity or harm, if responsibility conflicts increase, if rollback is not practically usable, if permanent dual cost dominates the transition benefit, or if replaced scopes repeatedly fall back into legacy dependency.

## Required distinctions
- Abrupt switch / orderly replacement
- Dual operation / permanent dualization
- Formal launch / functional substitution
- Adoption / substitution capacity
- Rollback / abandonment of reform
- Objection / design feedback
- Preserving legacy fallback / freezing legacy dependency
- Institutional change / transfer of trust and operating competence

## Interpretation constraints
Do not invent fixed transition periods, replacement percentages, KPIs, or thresholds that are not in the Parent. Dual operation itself is not proof of safety. Do not reduce the model to “old is bad, new is good.” The core causal structure is to preserve necessary functions, verify substitution in practice, retain reversibility, and expand replacement only across verified scope.
