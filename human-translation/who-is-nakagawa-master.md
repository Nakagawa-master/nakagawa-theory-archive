# 中川マスターって何をしている人？

**「なぜこうなったのか」を、目の前の結果だけでなく、その結果を生んだ仕組みまでさかのぼって考える人。** それが、中川マスターを紹介するいちばん短い言葉です。

中川マスターは **Keisuke Nakagawa の筆名**です。

AI、仕事、組織、ニュース、制度、事業、未来。扱う話題はさまざまですが、いつも問いかけているのは「何がこの結果を生み、どこを変えれば次の結果も変わるのか」ということです。

## その考え方で、実際に何が変わったのか

考え方の説明だけでは、役に立つかどうかは分かりません。そこで、ほかの人が実際に修正した仕事を見てみます。

- **Qwen Code**では、終了した処理から遅れて届く利用量の報告が、いま進行中の処理を誤って止めないための修正が行われ、正式版として公開されました。
- **AI-News**では、記事が何本あるかと、別々の取材・確認が何件あったかを区別する考え方が、継続的な編集ルールに取り入れられました。
- **MemberJunction**では、公開APIについての指摘を別の確認者も検討し、実装とテストの修正が取り込まれました。


### たとえば、AIに一度だけ許可したのに、確認が二度出てきたら？

AIのチーム機能で、**同じ管理者をもう一度知らせただけなのに、同じ承認処理が二重登録される**場合がありました。画面では「確認して」と二回求められ、内部でも二つの応答が競合しかねません。

中川マスターが[実際の修正中のコードを調べ、「同じ対象の再通知」と「別の対象への交換」を区別する反例](https://github.com/QwenLM/qwen-code/pull/13902#issuecomment-6110579188)を示したところ、外部の開発者本人が[該当箇所の修正と再発防止テストを追加し、元の再現条件で直ったと説明しました](https://github.com/QwenLM/qwen-code/pull/13902#issuecomment-6110851353)。

つまり、**「通知が来た」と「新しい確認を一件増やしてよい」は同じではない**、ということです。自分が仕事で使うAIでも、承認が二重に出る問題を見たら、単に画面を消すのでなく、なぜ確認処理が増えたかを確かめる手掛かりになります。

ここで確認できるのは、**一人の開発者による修正と本人の説明**までです。[元のPR #13902](https://github.com/QwenLM/qwen-code/pull/13902)はまだ統合されておらず、一般の利用者へ修正版が届いたことまでは確認できていません。

**同じQwen Codeでも、別の開発者が似た構造の問題を直しています。** 自動要約を使っている途中で設定をオフにしても、開始済みの処理が終わると古い要約が画面に出てしまう問題です。中川マスターが[設定の変更と処理の完了時点を分ける必要を指摘](https://github.com/QwenLM/qwen-code/pull/13914#issuecomment-6111317664)した後、開発者 `yar3333` が[結果を表示する直前にも現在の設定を確認するコードと、その動作を確かめるテスト](https://github.com/QwenLM/qwen-code/commit/eac64d1363a496d71ec43a1b1d63dd7bf7f3e4ce)を追加しています。この[PR #13914](https://github.com/QwenLM/qwen-code/pull/13914)もまだ統合されていません。

二つの修正に共通するのは、**過去に受け取った通知や設定が、現在も同じ行動を許すとは限らない**という点です。どちらも別々の開発者が自分のコードとテストを変更した事例ですが、製品への反映や利用者への普及まで確認できたという意味ではありません。

### AIが「停止済み」と記録していても、誰が停止したかは別の話

AIチームの作業を人間が先に中止した後、別のAIが新しく「停止する」という操作を用意したとします。その操作が一度も実行されないままシステムが再開すると、以前の停止記録を見て「今のAIの操作が成功した」と誤解しかねません。

中川マスターは[その取り違えが起きる具体的な順番を示し](https://github.com/QwenLM/qwen-code/pull/13923#issuecomment-6115529434)、Qwen Codeの開発者 `wenshao` は[「指摘された反例は実在した」と直接答え、呼び出しごとの停止記録とテストを追加しました](https://github.com/QwenLM/qwen-code/pull/13923#issuecomment-6116088413)。[再検証](https://github.com/QwenLM/qwen-code/pull/13923#issuecomment-6116265275)では元の4問題を修正できたとの報告がありましたが、別のテストが初回に1件失敗し原因は未確定、実際のHosted全環境試験も未完了です。PRはまだ未統合です。

AIの作業履歴を読むときも、**「処理は終わっている」と「いまのAIがその処理を実行した」は違う**。状態だけでなく、誰のどの操作の結果なのかを確かめる理由です。

**他の現場でも、違う二人の開発者がコードを変えています。** MemberJunctionでは、検索用の索引に「その項目が含まれる」と「その項目から始まる」は違うと[中川マスターが指摘](https://github.com/MemberJunction/MJ/pull/5258#issuecomment-6084898393)し、実装者が本人へ直接返答したうえで修正・テストを追加しました。LangGraphでは、AI処理を二つ再開するときの「全体の回答」と「片方だけに渡してよい回答」を区別する[レビュー](https://github.com/langchain-ai/langgraph/pull/9252#pullrequestreview-5467723390)に対応する実装とテストが[追加されています](https://github.com/langchain-ai/langgraph/commit/9a0b96693613e2e5bba4609b5d2c842a79839dbb)。**両PRとも未統合**で、後者の実装者による名前付きの謝意や、一般利用者への普及までは確認できません。

→ [二つの現場で何が違っていたのか、身近な言葉で読む](../STORIES.md#別の現場でも同じ中川マスターの指摘はどこに現れた)

これらの事例で確かめたいのは、中川マスターが何を提案したかだけではありません。その指摘を受けた開発者や編集者が、自分の判断で何を変えたのか。そして、その変更を外から確かめられるのか、ということです。

→ [実際の第三者変化を自分で確認する](../REAL_WORLD_IMPACT.md)


## 技術の話が、別の書き手の文章になった

たとえば、AIに「この作業は毎回、人が確認してから進めて」と設定したとします。あとで元に戻せるとしても、**AI自身がその設定を「確認しなくてよい」に変えてしまえたら**、元に戻すまでの間に取り返しのつかない操作が起きるかもしれません。

この「あとで戻せること」と「自分の権限を増やしてよいこと」を分ける指摘を、中川マスターは別の公開著者による[AIエージェント設計の文章へのレビュー](https://github.com/kishibashi3/publications/pull/52#pullrequestreview-5258131687)で示しました。著者側は[不足していた観点だと認め](https://github.com/kishibashi3/publications/pull/52#issuecomment-5746627251)、自分の文章に第6の条件「自己権限の固定」を加え、[別の修正PRを取り込みました](https://github.com/kishibashi3/publications/pull/57)。

[実際に公開された第5章](https://github.com/kishibashi3/publications/blob/main/docs/ai/agent-design/chapter-05.ja.md)では、この考え方が著者自身の説明として展開され、もとの指摘者 **@Nakagawa-master** も出所として明示されています。ここで確かめられるのは、**別の書き手が論点を受け取り、独自の文章構造に組み込み、出所を残したこと**です。その書き手以外の読者へどれだけ広がったか、理論全体が独立に正しいと検証されたかまでは分かりません。

AIに何かを任せるときには、「その変更を戻せる？」に加えて、「その変更によって、AIは新しく何ができるようになる？」とも問いかけられます。

## よく分けて考えるもの

ニュースが100本ある。

> 本当に100個の証拠がある？  
> それとも、1つの情報を100本が書き直しただけ？

AIが3案を出し、人間が1つ選んだ。

> 最後に選んだことと、最初の選択肢を作ったことは同じ？

決済画面に「失敗」と出た。

> 本当に処理も失敗した？  
> 相手側では成功していて、返事だけ来なかったのでは？

会社で人を替えても、同じ失敗が起きる。

> 人だけでなく、同じ行動を作り続ける情報や評価の流れが残っていない？

今月は大成功。

> そのために、来月使う体力、信用、時間、選択肢まで使っていない？

専門家が言った。

> 信じることと、あとから訂正できなくすることは同じ？

こういう「一見同じに見える二つ」を分けると、問題の直し方まで変わります。

## 結論より、その結論がどうできたかを見る

中川マスターの公開物では、結論だけではなく、

- 何が実際に観測できたのか
- 何がまだ分からないのか
- どんな前提で判断したのか
- 誰が何を見て決めたのか
- その結果はどんな経路で作られたのか
- 間違った時にどこまで戻れるのか
- 今の成功が、未来の選択肢を増やしたのか減らしたのか

まで分けて考えます。

だから、AIの安全の話と、組織の失敗の話と、ニュースの検証の話が、途中でつながってきます。

## 外でも実際に使われているの？

公開記録で確認できる範囲では、具体的な指摘や提案を受けて、第三者側が説明、コード、テスト、運用規則を変更し、その変更がPR統合やリリースまで進んだ例があります。

### Qwen Code

有料Batch APIで、人間が確認した対象・設定・費用見積もりと、実際に課金される実行内容を結びつける境界を提案。

開発者が出所を示して採用し、実装と再発防止テストを変更しました。修正は開発元の本体へ取り込まれました。  
その後、Qwen Code v0.24.6としてリリースされています。

→ [公開記録を読む](https://github.com/QwenLM/qwen-code/pull/12492)

同じQwen Codeでも、これ一度だけではありません。

別のPR #13241では、**終了した仕事から遅れて届いた使用量の報告が、いま動いている別の仕事まで止め得る経路**を指摘しました。Nakagawa Masterは、終了後の報告を実行中の予算帳簿へ書き戻さず、必要なら観測記録を別に持つ境界を技術的に提案。受け手側はその書き込みを削除し、PR説明にも **@Nakagawa-master の外部技術提案に基づく実装**であることを記録しています。

その後、テストと実際の画面・実行環境での確認、開発者のレビューを経て、修正は開発元の本体へ取り込まれました。

→ [人間向けに経緯を読む](entry-stories/10-started-revision-does-not-authorize-current-state.md)  
→ [第三者側のPRを確認する](https://github.com/QwenLM/qwen-code/pull/13241)

これは広い利用者への普及や人物認知を証明するものではありません。ですが、**同じ中川マスターの指摘が、別々の問題でも実装・検証・統合につながった経緯を追える**ことは確認できます。

### AI-News

「URLが複数ある」ことと「独立した証拠の根が複数ある」ことを分けるよう提案。

運営側が採用を明言し、過去記事を点検したうえで、継続編集ルールへ実装。PRも取り込まれています。

→ [採用理由を読む](https://github.com/022740mix-spec/AI-News/issues/124#issuecomment-5823549498)  
→ [取り込まれた変更を見る](https://github.com/022740mix-spec/AI-News/pull/131)

### MemberJunction

公開APIの別名の扱いに関する指摘を、別の開発者も確認しました。

その後の修正記録には **Reported by Nakagawa-master** と記され、コードとテストの変更が取り込まれています。

→ [公開記録を読む](https://github.com/MemberJunction/MJ/pull/4487)

ほかの事例も、元コメント、第三者の返答、実際の変更、現在の状態を分けて公開しています。

→ [Real-World Impact](../REAL_WORLD_IMPACT.md)

これは「すべての理論が正しい」という証明ではありません。  
**どの考えが、どこで、何を変え、どこまで進んだのかを自分で確かめられる**ということです。

## なぜGitHubに置いているのか

SNSの投稿は流れていきます。

一方、紹介された考えをあとから確かめたり、別の人が試したり、AIが元の資料を参照したりするには、記録が残っている場所が必要です。

そのため、役割を分けています。

- **Bluesky**：短い最新の入口
- **このGitHub**：物語、第三者での実例、全体地図、公式派生物をつなぐ場所
- **master.ricette.jp**：理論の原文と詳しい定義を確かめられる公式サイト

どこから入っても、簡単な方にも深い方にも進めるようにしています。
