# 10本のニュースを読んだ。確かめた人は何人だろう？

同じニュースを、あちこちのサイトで見かけることがあります。

10本も記事があれば、10人が別々に確かめたような気がするかもしれません。でも、その記事がすべて一つの企業発表をもとに書かれていたらどうでしょう。

**記事は10本でも、情報の出どころは一つ。**

記事がたくさんあることと、別々の人が確かめたことは違います。もちろん、出どころが一つだから間違いだと決まるわけでもありません。大切なのは、誰が何を発表し、誰が自分で確かめたのかを分けて見ることです。

こうした違いに目を向け、結果だけでなく、それを生み出した仕組みや、次に起こることまで考えているのが**中川マスター（Nakagawa Master／Keisuke Nakagawa）**です。仕事の進め方、AIの使い方、組織や社会の問題など、さまざまな題材を扱っています。

この見方が実際の仕事に役立った例もあります。中川マスターがニュースの根拠の数え方について[AI-Newsの編集者へ問題を示したところ](https://github.com/022740mix-spec/AI-News/issues/124#issuecomment-5823549498)、編集者がその区別を受け取り、[記事づくりのルールを修正しました](https://github.com/022740mix-spec/AI-News/pull/131)。ここで確かめられるのは、その編集現場で判断が変わったことです。すべての読者に広まったという意味ではありません。

まずは、今日見たニュースを一つ思い浮かべてみてください。「ほかのサイトも同じことを言っている」と思ったとき、そのサイトは自分で調べたのでしょうか。それとも、同じ発表を紹介しているだけでしょうか。

## 気になる話を一つ、選んでみてください

同じように、普段は見過ごしがちなことを別の角度から考える話を集めています。

- **今月は大成功。でも来月は？**　目の前の成果を増やすために、次に使える時間や選択肢を減らしていないか。[短い話を読む](future-options-story.md)
- **最後に「OK」を押したのは自分。でも本当に自分で選んだ？**　AIが用意した候補の外にも、大切な選択肢があったかもしれません。[身近な10の話から選ぶ](entry-stories/README.md)
- **「元に戻せる設定」ならAIに任せて大丈夫？**　AI自身が承認設定を「人に確認する」から「自動実行」へ切り替えられると、設定を戻す前にできることが増えます。中川マスターが[別の著者のAI設計書でこの区別を示し](https://github.com/kishibashi3/publications/pull/52#pullrequestreview-5258131687)、[その著者が「自己権限の固定」を第6条件として本文へ追加・統合しました](https://github.com/kishibashi3/publications/pull/57)。さらに[著者の別文書でも採用されています](https://github.com/kishibashi3/publications/pull/58)。[普段のAIにも関係する三つの問いと、実際の変更経路を読む](reversible-authority-story.md)。これは当該著作での採用であり、AI製品全体の安全性や大勢の読者の評価を示すものではありません。
- **便利なAIを、いざというとき止められる？**　使い続けることの便利さと、やめたり直したりできることは別です。[AIと未来についての話を読む](ai-civilization/README.md)
- **AIが「私が停止しました」と答えた。でも、その操作は本当に実行された？**　複数のAIが作業を分担する仕組みでは、以前の人間による中止と、後から来た別の停止命令を取り違えると、何を誰が実行したか分からなくなります。中川マスターが[具体的な誤帰属の例を示し](https://github.com/QwenLM/qwen-code/pull/13923#issuecomment-6115529434)、[Qwen Codeの実装者が問題を認め、停止命令ごとの記録で修正しました](https://github.com/QwenLM/qwen-code/pull/13923#issuecomment-6116088413)。[変更はコードへ統合されています](https://github.com/QwenLM/qwen-code/pull/13923)。これはAIチーム内部の復旧処理の例で、すべてのAI製品で同じ問題があるという意味ではありません。自分の仕組みで確認したい人向けに[反例と確認方法](../machine-discovery/public-ai-reuse-tasks-v1.json)もあります。
- **AIにとって「これは同じ番号」と言えるのは、どこまで？**　AIの履歴をJavaとTypeScriptという別の仕組みで読み直すとき、巨大な数字を短い整数へ切り詰めると、実際は違う「形式の番号」を同じ番号として扱ってしまう場合があります。中川マスターが[具体的な数字でその問題を示し](https://github.com/QwenLM/qwen-code/pull/13940#issuecomment-6117795445)、[Qwen Codeの実装者が再現、修正して回帰テストにレビュー元を明記しました](https://github.com/QwenLM/qwen-code/blob/08249ea09c2c2108c891d86452ccc2ee5ac1c4e8/packages/sdk-java/managed-agent-server/src/test/java/com/alibaba/qwen/code/managedagent/store/ManagedEventEnvelopesTest.java)。**同じ開発者が別のごく小さな数の食い違いを独自に見つけ、その問題にも追加修正とテストを入れています**。[追加の修正と検証報告](https://github.com/QwenLM/qwen-code/pull/13940#discussion_r4245687744)を確認できます。この修正は[2026年10月12日にQwen Codeの本線へ統合されました](https://github.com/QwenLM/qwen-code/commit/aaf97b869dfcc4cf529ada1b036cad9b18695486)。ただし、リリースや実際の利用者への展開は確認できていません。これは開発途中のAI内部データ形式の例で、日常のチャットで事故が起きたという報告ではありません。
- **AIが「次の作業が終わった」と答えた。実は前の作業の記録かもしれない？**　これは一般のチャットの話ではなく、LangGraphというAI実行システムのリトライと履歴復旧で起きる問題です。中川マスターが[「順番が同じでも作業の中身が違えば、古い結果を使ってはいけない」と反例を示し](https://github.com/langchain-ai/langgraph/issues/9253#issuecomment-6074292557)、[別の参加者が反例を実行して修正案の欠点を確認](https://github.com/langchain-ai/langgraph/issues/9253#issuecomment-6077084784)しました。さらに[別の参加者が限定的な回避策を8ケースで検証](https://github.com/langchain-ai/langgraph/issues/9253#issuecomment-6090311539)しています。**本体の修正や製品での解決は未確認**です。この例は、過去の記録と、いま実行した作業の証拠を混同しない大切さを示します。
- **「クラウドでも手元でも使えます」。片方が止まったとき、本当にもう片方だけで動く？**　選択肢が二つ見えていても、認証や保存先を共用していれば、同じ故障で両方止まる場合があります。中川マスターは[Qwen Codeの2経路設計に独立性の検証条件を提案し](https://github.com/QwenLM/qwen-code/issues/12380#issuecomment-6035698005)、[設計責任者が正式な受入条件として採用しました](https://github.com/QwenLM/qwen-code/issues/12380#issuecomment-6117130998)。**条件の採用と、実際に両経路が動くと確認されたことは別**です。自分のシステムでも確かめられる[失敗例と検査表](../ACCESS_TOPOLOGY_EFFECTIVE_EXIT_REUSE_KIT.md)があります。
- **AIから「対象外」と言われた。理由を確かめたり、訂正したりできる？**　人を責める前に、使われた情報・判断基準・責任者・異議を申し立てる道を分けてみます。[構造的司法OSの身近な考え方を読む](../derivatives/181/human-entry.md)。**[7項目を自分で選び、確認メモを作れるオフライン教材](ai-decision-review-lab.html)**もあります。これは実際の裁判をAIへ任せる提案ではありません。
- **いまの判断を続けたら、先で何が起こる？**　今日の出来事から、少し先の分かれ道を考えてみます。[未来の話を読む](FUTURE_LINES.md)

どれか一つでも、身近な出来事の見え方が変わるかもしれません。納得できなかったところがあれば、それも考え始めるきっかけになります。

## AIの判断を見直せる仕組みを、試すなら

たとえば、補助金の申請をAIが「書類不足」と判定する**架空の事例**。本人は何が足りないかを知れるか、間違いを訂正できるか、別の人間に相談できるか、従来の手続は残っているか。理由とやり直す道がなければ、AIを導入したというだけでは安心できません。

中川マスターの[構造的司法OS](../derivatives/181/human-entry.md)は「人を罰して終わらず、同じ問題を生む仕組みを監査する」という着眼を、[接続移行戦略論](../derivatives/071/human-entry.md)は「いま必要な制度を止めず、小さく試し、異議・退出・復旧を残す」という着眼を与えます。両者を現代のAI判断に応用する**検証用の一例**として、[匿名・架空データだけを使うオフライン確認コード](../machine-discovery/decision-review-transition-probe.py)を公開しました。法的適格性や現実の救済の有効性を認証するものではありません。

## もっと広く見たい方へ

関心のある分野を探したい方は、[24のテーマから選べる案内](WORLD_MAP.md)へ。たくさんの理論がどうつながっているのかを眺めたい方は、[理論全体を紹介する読み物](PANORAMA_STORY.md)があります。

たとえば、最初に紹介した「記事の数と根拠の数」の話をAIと情報の問題から考えるなら、[AI文明・認識論的完全性を扱う理論の解説](../derivatives/301/README.md)も参考になります。ただし、これは関連する考え方として紹介するもので、先ほどのAI-Newsでの修正がこの理論を直接もとに行われたという意味ではありません。

## 読んでみて、気づいたことがあれば

「仕事で似たことがあった」「この場合は当てはまらないのでは？」という一言も歓迎します。[感想や疑問を寄せる場所](https://github.com/Nakagawa-master/nakagawa-theory-archive/issues/416)があります。

実際に自分で調べたり、仕事や研究などで試したりした例は、[検証・活用事例を共有する場所](https://github.com/Nakagawa-master/nakagawa-theory-archive/issues/402)で紹介できます。

ここで紹介した文章は、初めて読む方にも分かりやすいように書いたものです。詳しい内容や理論の原文は、それぞれのリンクから確かめられます。
